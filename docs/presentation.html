MLOps • NYC taxi demand

From taxi trips to a recoverable forecast

An end-to-end system for hourly pickup demand by zone

The problem: a model can be accurate today and unreliable tomorrow. This project adds the data, monitoring, evaluation, and recovery loop around the model.

A reproducible local demonstration using NYC TLC Yellow Taxi data, Jan–Apr 2024.

01 • Problem and system

One system, from raw trips to recovery

The local demo simulates drift; it does not represent live production traffic.

02 • Design choices

Choices made for a reproducible time-series workflow

Chronological evaluation

Jan–Feb train; March reference; April later period. Retraining holds out the final 20% of April hours.

Why: avoids training on future observations when evaluating earlier ones.

One tabular regressor

HistGradientBoostingRegressor learns nonlinear interactions among zone, calendar, and recent-demand lags.

Why: a practical baseline for structured features, without requiring a separate deep-learning stack.

DVC + MLflow

DVC records data fingerprints; MLflow records runs, metrics, model artifacts, and registry versions.

Why: data lineage and experiment/model lineage solve different reproducibility needs.

Champion / candidate

Serving stays on @champion while a candidate is evaluated against it on the same holdout.

Why: training a model should not automatically put it into service.

03 • Trade-offs accepted

Pragmatic choices—with explicit limits

PSI is a warning, not quality

It detects distribution change in three lag inputs. PSI > 0.2 triggers investigation; it does not prove forecast error increased.

Synthetic drift is repeatable

The ×3 lag transform reliably fires the alert. It is not evidence that natural April data drifted.

Simple local infrastructure

SQLite MLflow and local artifacts keep the demo easy to run, but are not shared, highly available, or production-ready.

Manual operational steps

The watcher is a script; rollback is a command; the API must restart to load a changed champion alias.

Demo labels arrive immediately

Replay labels come from the dataset. Real delayed outcomes need a durable production source and an ingestion process.

Local data, no shared DVC remote

Data can be recreated from TLC; another machine cannot pull it from a shared DVC store yet.

Quality gate: require at least 1% MAE improvement and allow at most 2% WAPE regression. These are project thresholds, not universal constants.

05 • If I had more time

Move from reproducible demo to operational system

1. Share and reproduce

  • Provision a shared DVC remote and test a fresh-machine pull.
  • Use shared MLflow tracking/artifact storage and back up the registry.
  • Get instructor approval for team scope and grant repository access.

2. Evaluate real outcomes

  • Ingest delayed labels from a durable outcome source.
  • Track model-version cohorts over time and compare against baselines.
  • Set explicit review and rollback policies using labeled quality.

3. Harden operations

  • Run the watcher as a managed job with retries, health checks, and audit logs.
  • Test deployment and rollback without manual API restarts.
  • Add alert runbooks and failure-injection tests.

4. Improve data/model rigor

  • Handle timezone and daylight-saving transitions explicitly.
  • Compare against seasonal-naive and alternative model baselines.
  • Evaluate across more months and zones before production claims.
Takeaway: the project demonstrates the full feedback and recovery loop; the next step is real shared infrastructure and real delayed outcomes.
